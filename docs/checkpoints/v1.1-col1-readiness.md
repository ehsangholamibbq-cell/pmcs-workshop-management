## Contract and boundaries

`Pmcs.Modules.Collaboration` owns the project room, message, edit history, reaction, pin,
read cursor, moderation record, notification intent and conversion lineage. It never
owns Identity membership, Document bytes or official Action/Issue/RFI/Fact/Evidence/
Technical Document state. One deterministic default room exists per project. A room
cannot be independently invited into, made public or addressed to a person. All
requests carry the authenticated tenant and actor; the project path is checked
against the current active membership through an Identity application contract,
including tenant administrators. The room ID is server derived, not a caller supplied
scope. Revocation or suspension takes effect on every read, write, hub join,
reconnect, document access and conversion request.

Permissions are `collaboration.read`, `send`, `upload`, `edit-own`, `moderate` and
`convert`, all project scoped. Read does not imply Send. Membership is necessary
even for an actor whose tenant role grants a permission; permission is separately
necessary for each operation. An offline client cannot grant itself access.

Messages are contextual and unofficial. Server sequence is monotonic per room and
pagination uses a `(sequence, id)` cursor. A stable client message UUID is unique
per tenant/project/actor; identical retries return the original message and a
changed retry payload conflicts. The server stores UTC timestamps and renders
Persian dates only at the UI boundary. Reply targets, mentions, files and all
lookup IDs must belong to the same tenant/project/room; cross-scope lookup fails
closed without revealing content. Message text is bounded plain text, rendered
without HTML interpretation. Search is permission filtered and excludes redacted
content. Event payloads contain IDs and safe metadata, never message or file bytes.

Edit Own is bounded to the author, keeps immutable prior revisions and preserves
Audit. Delete is a visible tombstone with preserved history and Audit; moderators
may redact abusive content with a recorded reason. Retention is configured by
tenant policy; until a reviewed policy is configured, automated content purge is
disabled. Legal Hold overrides expiry and deletion. No physical purge, including
of attachment bytes, may run before the retention and legal-hold gate is qualified.
This is a safe default, not a business retention-duration decision.

Attachments use the Shared Document Foundation owner contract, private storage,
hash/signature validation, quarantine and read recheck. A released document is
necessary before association and download. A tombstone does not bypass retention
or remove a derived official record. Explicit conversion requires Human
Confirmation, the destination module's application command and permission,
validation and idempotency. A conversion failure has no official side effect;
success preserves message revision, document IDs/hashes, actor, UTC timestamp and
destination reference in lineage. Chat cannot update finance, schedule, progress,
approval or project state directly.

No DM, voice/video, public feed, autonomous bot or general-purpose messenger UI.
Dedicated visual design for Chat and Reporting remains owned by UX2.

source candidate passes all required gates. A failed candidate stays in
Development and is corrected with a new commit; no reset or force push.

## Dependencies, rollout and ownership

- Identity Access owns the current active membership and permission decision;
  Collaboration calls it through an interface, never its DbContext.
- Documents owns bytes, scan/quarantine, classification, retention and legal hold;
  Collaboration only stores document references and verifies owner/scope.
- Destination modules own their conversion commands. Unsupported conversion
  must fail explicitly, without a placeholder official record.
- Default rollout is disabled until COL1 qualification; history survives disable
  and runtime rollback. Migration is additive and ordered after the 56 existing
  migrations. Feature flag does not authorize bypassing permission.
- Real-time delivery is advisory; durable database sequence and read API are
  authoritative. Clients reconcile after reconnect, account/permission change
  or a gap and never infer delivery from a hub broadcast alone.
- UX2 owns the full Chat UI migration; QA1 owns cross-module final qualification,
  real pilot/UAT and V1.1 lock. This DoR does not close those gates.

## Exit criteria

COL1 closes only with real-time/reconnect/ordering, duplicate prevention,
concurrent actors, membership suspension, files, offline retry, search, audit and
each official conversion independently evidenced in connected tests. The
feature is not Production enabled by a green build alone.
